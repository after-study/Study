# CHAPTER 06 코딩하는 동안 해야 할 일들

설계가 끝나면 코딩은 그걸 기계적으로 옮기는 일이라는 생각이 흔하다. 저자들은 이 태도가 엉망인 프로그램이 많은 가장 큰 원인이라고 본다.
코딩은 기계적인 작업이 아니다. 매 순간 판단을 내려야 하는 일이다. 운전처럼 대부분은 반복이지만, **늘 깨어 있어야** 사고를 막는다.

- 왜 돌아가는지 모르는 코드 → 우연에 맡기는 프로그래밍
- 데이터가 커지면 터지는 코드 → 알고리즘의 속도
- 계속 자라나는 코드 → 리팩터링
- 검증할 수 없는 코드 → 테스트하기 쉬운 코드
- 내가 안 쓴 코드 → 사악한 마법사

### 우연에 맡기는 프로그래밍

> **TIP 44. 우연에 맡기는 프로그래밍을 하지 말라.**

지뢰밭 앞의 병사가 총검으로 땅을 찔러보며 조금씩 나아가다가, 아무것도 없으니 안심하고 걷기 시작한 순간 지뢰를 밟는다. 처음에 안 터진 건 운이었을 뿐이다.

프레드는 코드를 조금 짜고 돌려보고, 되네? 조금 더 짜고 돌려보고, 되네? 그렇게 몇 주를 가다가 갑자기 안 돌아간다. 원인을 모른다. **처음부터 왜 돌아가는지 몰랐으니까.**

**우연적 구현** — 지금 구현이 우연히 그렇게 동작하는 것에 기대는 것.

- 문서화되지 않은 동작, 잘못된 데이터에 대한 우연한 반응에 의존한다. 라이브러리 작성자가 그걸 "고치면" 내 코드가 깨진다.
- 화면에 뭔가 띄우려고 `paint()`, `invalidate()`, `validate()`, `revalidate()` ... 다 불러봤더니 됐다. 그리고 "되니까 건드리지 말자" 하고 그대로 둔다.
- 건드려야 하는 이유: 진짜 되는 게 아닐 수 있고, 다른 환경(해상도 등)에서 다르게 동작할 수 있고, 다음 버전에서 바뀔 수 있고, 쓸데없는 호출은 느리고 버그를 부른다.
- **남의 루틴은 문서화된 동작에만 기대자.** 어쩔 수 없이 다른 걸 기대야 한다면 문서로 남기자.

**우연적 맥락** — GUI 환경에서 쓸 거라고 유틸 모듈이 GUI를 필요로 해야 할까? 사용자가 늘 영어를 쓴다고, 글을 읽을 수 있다고 가정하고 있진 않나?

**암묵적인 가정** — "Y의 원인은 X겠지"라고 가정하기 쉽다. 가정은 문서화되는 일이 드물고 사람마다 다르다. 가정하지 말고 증명하자.

**의도적으로 프로그래밍하기**

- 내가 지금 뭘 하고 있는지 항상 알자. (안 그러면 삶은 개구리가 된다)
- 이해 못 한 앱, 익숙하지 않은 기술로 맹목적으로 코딩하지 말자.
- 계획을 세우고 진행하자. 머릿속이든 냅킨이든 상관없다.
- 신뢰할 수 있는 것에만 기대자. 판단이 안 서면 최악을 가정하자.
- 가정을 문서로 남기자. (계약에 의한 설계)
- 코드뿐 아니라 **가정도 테스트**하자. 단정문(assertion)으로 확인하자. 맞으면 문서화가 된 거고, 틀리면 일찍 찾아서 다행인 거다.
- 중요한 것부터 하자. 기반이 틀렸으면 화려한 기능도 소용없다.
- **과거의 노예가 되지 말자.** 기존 코드가 앞으로의 코드를 지배하게 두지 말고 언제든 리팩터링할 자세를 갖자.

(Stack Overflow나 AI가 준 코드를 붙여넣고 "돌아가니까 됐다" 하는 게 딱 프레드다...)

### 알고리즘의 속도

> **TIP 45. 여러분 알고리즘의 차수를 추정하라.**
> **TIP 46. 여러분의 추정을 테스트하라.**

레코드 1,000개는 괜찮은데 100만 개면? 이런 질문은 상식, 약간의 분석, 그리고 **Big-O 표기법**으로 답할 수 있다.

**O() 표기법** — 근사치를 다루는 방법. 최악의 경우 입력 n이 커질 때 시간(혹은 메모리)이 얼마나 빨리 늘어나는지의 상한이다. 최고차항만 남기고 상수는 버린다. `O(n²/2 + 3n)` = `O(n²)`.
약점도 있다. 같은 `O(n²)` 이라도 하나가 다른 것보다 천 배 느릴 수 있는데 표기로는 안 보인다.

100개 처리에 1초 걸리는 루틴이 1,000개를 처리하면

| 차수 | 예 | 1,000개일 때 |
|---|---|---|
| O(1) | 배열 원소 접근 | 1초 |
| O(lg n) | 이진 검색 | 약 1.5초 |
| O(n) | 순차 검색 | 10초 |
| O(n lg n) | 퀵정렬/힙정렬 평균 | 약 15초 |
| O(n²) | 선택/삽입 정렬 | 100초 |
| O(2ⁿ) | 외판원 문제 | 우주가 끝날 때까지... |

**상식으로 추정하기**

- **단순 반복문** (1부터 n까지) → `O(n)`. 최대값 찾기, 체크섬.
- **중첩 반복문** → `O(m × n)`. 버블 정렬 같은 단순 정렬.
- **반씩 잘라 나가기** → `O(lg n)`. 이진 검색, 이진 트리 탐색.
- **분할 정복** (나눠서 처리하고 합치기) → `O(n lg n)`. 퀵정렬. (이미 정렬된 입력이면 최악 `O(n²)`)
- **조합적** (순열을 다루기 시작하면) → 폭발한다. 5개 → 6개면 6배, 7개면 42배.

**실전에서는**

- 정렬 루틴을 직접 짤 일은 별로 없다. 하지만 반복문을 짤 때마다 "이 n이 얼마나 커질 수 있지?"는 물어보자. 외부 요인(어젯밤 배치 레코드 수, 사용자 수)에 따라 달라지는 값이라면 한번 멈춰서 생각하자.
- 확실하지 않으면 입력 크기를 바꿔가며 직접 돌려보고 그래프로 그려보자. 점 서너 개면 곡선 모양이 보인다.
- 이론만 믿지 말자. 메모리가 꽉 차서 스왑을 쓰기 시작하면 선형이던 게 갑자기 치솟는다. 랜덤 데이터로만 테스트하다가 정렬된 입력이 들어오면 놀랄 수 있다. **실제 데이터로 운영 환경에서 돈 시간만이 진짜 숫자다.**

**최고가 언제나 최고는 아니다**

- 입력이 작으면 삽입 정렬이 퀵정렬과 별 차이 없고, 짜고 디버깅하기는 훨씬 쉽다.
- 데이터를 알고리즘에 맞게 준비하는 비용이 알고리즘 실행보다 클 수도 있다.
- **성급한 최적화를 조심하자.** 진짜 병목인지 먼저 확인하자.

### 리팩터링

> **TIP 47. 일찍 리팩터링하고, 자주 리팩터링하라.**

소프트웨어 개발은 흔히 **건축**에 비유된다. 설계자가 도면 그리고 → 시공하고 → 입주자가 산다. 하지만 소프트웨어는 오히려 **정원 가꾸기**에 가깝다. 심어보고, 잘 안 자라면 옮기고, 너무 크면 나누고, 잡초는 뽑고, 계속 지켜보며 조정한다.

**언제 리팩터링하나?** 뭔가 "잘못됐다" 싶으면 바로 지금.

- 중복 (DRY 위반)
- 직교적이지 않은 설계
- 유효기간이 지난 지식 (요구사항이 바뀌었고, 문제에 대한 이해가 깊어졌다)
- 성능 (기능을 다른 곳으로 옮겨야 한다)

**현실의 문제** — "돌아가긴 하는데 리팩터링하게 일주일 더 주세요" 하면 무슨 대답이 돌아올지 뻔하다. 하지만 지금 안 하면 의존성이 더 쌓인 뒤에 훨씬 큰 비용을 치른다. 그때 일정이 더 여유로울까? 그런 일은 없다.

윗분을 설득할 땐 **종양**에 비유해보자. 작을 때 떼면 간단한데, 퍼질 때까지 두면 수술이 커지고 위험해진다.

당장 못 하면 리팩터링할 목록을 관리하고 일정에 확실히 넣어두자. 그 코드를 쓰는 사람들에게도 곧 바뀔 거라고 알려두자.

**어떻게 하나?** (마틴 파울러의 조언)

1. **리팩터링과 기능 추가를 동시에 하지 말자.**
2. 시작 전에 **든든한 테스트**가 있는지 확인하고, 최대한 자주 돌리자.
3. **작은 단계**로 나눠서 신중하게. 한 단계 끝날 때마다 테스트.

인터페이스가 호환되지 않게 바뀌는 큰 변경이라면, 일부러 빌드가 깨지게 만들어서 의존하는 코드를 컴파일러가 다 찾아주게 하는 것도 방법이다.

**고통을 관리하라.** 지금 아파도 나중에 더 아플 거라면 지금 고치자. 깨진 창문을 내버려두지 말자.

(책이 나올 때는 자동 리팩터링이 스몰토크에만 있었는데, 지금은 IDE의 Rename, Extract Method가 당연한 기능이 됐다.)

### 테스트하기 쉬운 코드

> **TIP 48. 테스트를 염두에 두고 설계하라.**
> **TIP 49. 소프트웨어를 테스트하라. 그렇지 않으면 사용자가 테스트하게 될 것이다.**

하드웨어 칩은 공장에서도, 회로에 꽂은 뒤에도, 현장에서도 테스트할 수 있게 설계된다. (자체 진단 기능, 테스트 핀) 소프트웨어도 **처음부터 테스트 가능성을 넣어서** 만들고, 조립하기 전에 부품 하나하나를 철저히 테스트하자.

**단위 테스트 = 계약 테스트** — 아무 데이터나 넣어보고 "테스트했다"고 하지 말고, 계약을 지키는지 확인하자. 예를 들어 제곱근 함수라면

- 음수를 넣으면 거부하는가?
- 경계값 0은 받아들이는가?
- 0과 최대값 사이 값을 넣으면 결과의 제곱이 원래 값과 허용 오차 안에 있는가?

모듈 A가 LinkedList와 Sort를 쓴다면, **LinkedList → Sort → A** 순서로 하위 컴포넌트부터 테스트한다. 하위가 다 통과했는데 A만 실패하면 문제는 A 안에 있다. 디버깅 범위가 확 줄어든다.

테스트를 먼저 생각하며 설계하면 미처 생각 못 했을 경계 조건이 보인다. 코드보다 테스트를 먼저 짜면 인터페이스가 굳기 전에 미리 써볼 수 있다. (→ TDD)

**단위 테스트 작성하기**

- 테스트는 **찾기 쉬운 곳**에 두자. 구석에 처박혀 있으면 아무도 안 돌린다.
- 테스트 코드는 그 자체로 (1) 모듈을 어떻게 쓰는지 보여주는 **예제**이고, (2) 나중에 변경했을 때 확인할 **회귀 테스트**다.
- 만들기만 하지 말고 **자주 돌리자.**

**테스트 장치(harness)** 가 갖춰야 할 것

- setup / teardown을 지정하는 표준 방법
- 테스트를 골라서 또는 전부 실행하는 방법
- 예상 결과와 비교해 분석하는 방법
- 실패를 보고하는 표준 형식
- 테스트를 조립할 수 있어야 한다. (테스트 스위트 안에 테스트 스위트)

→ 이미 다 만들어 둔 게 JUnit 같은 xUnit 계열이다.

**임시변통 테스트도 버리지 말자** — 디버깅하면서 그 자리에서 짠 테스트는 정식 단위 테스트로 옮겨두자. 한 번 깨진 곳은 또 깨진다.

**테스트 윈도우 만들기** — 아무리 테스트해도 현장에서만 나오는 버그가 있다. 배포 후에도 내부를 들여다볼 창을 만들어 두자.

- 일관된 형식의 로그 (자동으로 파싱할 수 있게)
- 숨은 단축키로 여는 진단 창 (고객 지원용)
- 서버라면 내장 웹 서버로 상태와 로그를 보는 페이지

**테스트 문화** — 펄은 `make test` 가 표준이다. 언어보다 중요한 건 테스트가 정해진 곳에 있고, 예측 가능한 결과를 낸다는 **문화**다. 우리가 테스트 안 하면 결국 사용자가 테스트한다.

(요즘의 Jest/Vitest, CI에서 PR마다 테스트 돌리기, 헬스체크 엔드포인트, 모니터링 대시보드가 다 이 이야기의 연장선이다.)

### 사악한 마법사

> **TIP 50. 자신이 이해하지 못하는, 마법사가 만들어 준 코드는 사용하지 말라.**

앱은 점점 복잡해지고 도구 회사들은 **마법사(wizard)** 를 내놨다. 버튼 하나 누르고 질문 몇 개에 답하면 골격 코드가 1,200줄씩 생긴다.

문제는 전문가가 만든 마법사를 쓴다고 내가 전문가가 되는 게 아니라는 것.

- 그럴싸한 코드가 잔뜩 생기니 잘하고 있는 것 같지만, 이해 못 하면 **우연에 맡기는 프로그래밍**이다.
- 마법사는 일방통행이다. 코드를 만들어주고 끝. 상황이 바뀌어 고쳐야 할 때는 혼자서 해야 한다.
- 이해 못 한 코드는 유지보수도, 디버깅도 못 한다. 그럼 그 앱의 주인은 내가 아니다.

"우리도 집적회로의 양자역학이나 OS 스케줄러는 다 모르고 쓰잖아?" 라는 반론이 있다. 맞다. 하지만 그런 것들은 **깔끔한 인터페이스 뒤에** 있는 라이브러리나 OS 서비스다. 마법사가 만든 코드는 내 코드와 **한 줄 한 줄 섞여서** 결국 내 코드가 된다. 그리고 누구도 자기가 완전히 이해하지 못하는 코드를 내놓아서는 안 된다.

(이 꼭지는 지금 다시 읽으면 AI 코딩 도구 이야기로 들린다. 마법사보다 훨씬 많은 코드를, 훨씬 그럴싸하게 만들어 준다.)

### 서로 이야기 해볼 것.
