# CHAPTER 05 구부러지거나 부러지거나

세상은 계속 변하고 코드도 따라 변해야 한다. 딱딱한 코드는 변화를 만나면 부러지고, 유연한 코드는 구부러진다.
2장 「가역성」이 "되돌릴 수 없는 결정은 위험하다"는 이야기였다면, 이번 장은 **되돌릴 수 있게 만드는 구체적인 방법**에 대한 이야기다. 핵심 키워드는 하나, **결합도(coupling) 줄이기**.

- 모듈끼리 덜 알게 하자 → 디미터 법칙
- 세부사항을 코드 밖으로 빼자 → 메타프로그래밍
- "A 다음에 B"라는 시간 의존을 끊자 → 시간적 결합
- 데이터와 보여주는 방식을 나누자 → 모델/뷰 분리
- 서로 몰라도 협업하게 하자 → 칠판

### 결합도 줄이기와 디미터 법칙

> **TIP 36. 모듈 간의 결합도를 최소화하라.**

스파이 조직은 "세포" 단위로 움직인다. 같은 세포원끼리만 알고 다른 세포는 모른다. 하나가 잡혀도 나머지는 안전하다. 코드도 마찬가지로 모듈을 세포처럼 나누고 상호작용을 제한하면, 하나를 바꾸거나 교체해도 나머지는 그대로 돌아간다.

집 리모델링을 맡길 때 주계약자 한 명과 계약하면, 하도급자들은 주계약자가 알아서 관리한다. 내가 하도급자와 직접 씨름할 필요가 없다. 객체에게 뭔가를 요청할 때도 **"알아서 처리해줘"** 가 되어야지, 객체를 넘겨받아서 그 안을 헤집고 다니면 안 된다.

```java
// 나쁜 예: 남의 내부 구조를 줄줄이 타고 들어간다
selection.getRecorder().getLocation().getTimeZone();

// 좋은 예: 필요한 걸 직접 물어본다
selection.getTimeZone();
```

첫 번째 코드는 `Selection`, `Recorder`, `Location` 세 클래스 구조에 모두 의존한다. 누가 `Location` 구조를 바꾸면 내 코드도 같이 고쳐야 한다.

**디미터 법칙** — 어떤 메서드는 아래에 해당하는 것의 메서드만 호출해야 한다.

- 자기 자신
- 메서드로 넘어온 인자
- 자신이 생성한 객체
- 자신이 직접 갖고 있는 객체

불필요한 의존이 많을 때 나타나는 징후

- 단위 테스트 하나 돌리려고 시스템 전체를 끌고 와야 한다.
- 한 모듈의 "간단한" 수정이 상관없는 모듈들까지 퍼져나간다.
- 고쳤을 때 어디가 터질지 몰라서 코드 수정이 무섭다.

**대가도 있다.** 디미터 법칙을 지키려면 단순히 요청을 전달만 하는 위임 메서드가 잔뜩 생긴다. 성능이나 메모리가 중요한 곳에서는 일부러 결합을 허용할 수도 있다. DB 반정규화처럼, **알고 받아들인 결합**이라면 괜찮은 설계다. 모르고 생긴 결합이 문제다.

> 물리적 결합도 있다. 파일, 디렉터리, 라이브러리 간 의존(특히 순환 의존)을 방치하면 빌드 한 번에 몇 시간씩 걸리는 프로젝트가 된다.

(요즘으로 치면 `a?.b?.c?.d` 처럼 옵셔널 체이닝이 길게 늘어진다면 디미터 법칙 위반 냄새가 난다고 볼 수 있다.)

### 메타프로그래밍

> **TIP 37. 통합하지 말고 설정하라.**
> **TIP 38. 코드에는 추상화를, 메타데이터에는 세부 내용을.**

비즈니스 규칙, 법, 윗분들의 취향... 세부사항은 자주 바뀌고, 바뀔 때마다 코드를 고치면 버그가 생길 기회를 준다. 그러니 **세부사항을 코드 밖으로 몰아내자.**

**메타데이터**는 "데이터에 관한 데이터"인데, 이 책에서는 더 넓게 **애플리케이션을 기술하는 모든 데이터**를 말한다. 어떻게 실행될지, 어떤 자원을 쓸지 같은 것들. 보통 컴파일 타임이 아니라 런타임에 읽는다.

- 배경색, 문구 같은 사소한 것뿐 아니라 알고리즘 선택, DB 제품, 미들웨어, UI 스타일까지 설정으로 빼자.
- 일반적인 경우는 코드로 만들고, 특수한 경우는 코드 밖에 둔다. "어떻게"가 아니라 "무엇을" 하는지 선언적으로 생각하자.

이렇게 하면

- 결합도가 줄어 유연해진다.
- 세부사항이 빠지니 설계가 더 추상적이고 단단해진다.
- 커스터마이징하려고 다시 컴파일할 필요가 없다. 운영 중 버그도 설정으로 우회할 수 있다.
- 같은 엔진에 메타데이터만 바꿔서 여러 프로젝트에 쓸 수 있다.

**비즈니스 로직**도 대상이다. "중소 공급자는 45일, 대형 공급자는 90일 안에 대금 지급" 같은 정책은 언제든 바뀐다. 코드에 박지 말고 설정으로 만들자. 규칙이 많고 복잡하면 룰 엔진을 고려하자.

**언제 설정을 읽을까?** 시작할 때 한 번만 읽으면 설정 바꿀 때마다 재시작해야 한다. 오래 도는 서버라면 실행 중에도 다시 읽을 수 있게 만들자. 금방 재시작하는 작은 클라이언트라면 굳이 그럴 필요 없다.

> **도도 코드를 작성하지 말라.** 환경에 적응하지 못한 도도새는 멸종했다. 적응하지 못하는 코드도 마찬가지.

(Feature Flag, `.env`, 원격 설정으로 배포 없이 동작을 바꾸는 게 바로 이 이야기다.)

### 시간적 결합

> **TIP 39. 작업흐름 분석을 통해 동시성을 개선하라.**
> **TIP 40. 서비스를 사용해서 설계하라.**
> **TIP 41. 언제나 동시성을 고려해 설계하라.**

설계할 때 "시간"이라고 하면 보통 마감일만 생각한다. 여기서 말하는 시간은 설계 요소로서의 시간이다.

- **동시성**: 같은 시각에 일어나는 일들
- **순서**: 일들의 상대적인 위치

사람은 보통 "이거 하고, 그 다음 저거" 식으로 직선적으로 생각한다. 그러다 보면 "A는 반드시 B보다 먼저 호출돼야 한다" 같은 **시간적 결합**이 생긴다. 유연하지도 않고 현실적이지도 않다.

**작업흐름** — 피냐콜라다 만들기를 순서대로 12단계로 적어도, 활동 다이어그램으로 그려보면 "믹서 열기 / 병뚜껑 열기 / 럼 계량 / 잔 가져오기 / 장식 가져오기"는 동시에 할 수 있다. 진짜 의존성이 어디 있는지 그려보면 의외로 병렬화할 게 많다.

**아키텍처** — 저자들이 만든 트랜잭션 처리 시스템은 입력 처리, 애플리케이션 로직, DB 처리를 각각 독립 프로세스로 두고 **작업 큐**로 비동기 통신하게 했다. 입력 프로세스는 요청을 큐에 넣고 바로 다음 입력을 받으러 간다.

- **배고픈 소비자(hungry consumer) 모델**: 중앙 스케줄러 없이, 소비자들이 큐에서 일을 하나씩 가져가 처리하고 끝나면 또 가져간다. 하나가 느려도 다른 소비자들이 계속 일을 처리한다. 각자 자기 속도로 일한다.
- 이건 컴포넌트가 아니라 **서비스**, 즉 잘 정의된 인터페이스 뒤에서 독립적으로 동시에 도는 객체를 만든 것이다.

**동시성을 고려한 설계**

- 전역/정적 변수는 동시 접근에서 보호해야 한다. 애초에 왜 전역이 필요한지 다시 생각해 볼 기회다.
- 객체는 **호출될 수 있는 모든 순간에 유효한 상태**여야 한다. 생성자와 초기화 메서드가 분리돼서 "생성은 됐는데 아직 초기화 전" 같은 상태가 있다면, 그 사이에 아무도 안 부를 거라는 **우연**에 기대는 셈이다.

**더 깔끔한 인터페이스** — C의 `strtok`은 내부에 숨은 상태를 갖고 있어서 두 문자열을 번갈아 파싱할 수 없다. 반면 Java의 `StringTokenizer`는 인스턴스마다 상태를 가지니 여러 개를 동시에 써도 문제없다. 동시성을 고려하면 인터페이스가 자연스럽게 깔끔해진다.

**배치** — 처음부터 동시성을 고려해 설계하면 단독 앱, 클라이언트-서버, n-티어 어떤 형태로든 배치할 수 있다. 반대로 동시성 없는 앱에 나중에 동시성을 끼워 넣는 건 훨씬 어렵다.

(JS의 Promise/async, 메시지 큐(SQS, Kafka) 기반 워커 구조가 배고픈 소비자 모델 그 자체다.)

### 단지 뷰일 뿐이야

> **TIP 42. 모델에서 뷰를 분리하라.**

모듈을 책임별로 나눴다면, 이제 런타임에 그것들이 어떻게 서로 이야기하게 할지가 문제다. 서로를 너무 많이 알면 안 된다.

**이벤트** — "방금 뭔가 흥미로운 일이 일어났다"는 메시지. 보내는 쪽은 받는 쪽을 몰라도 된다. 다만 초기 Java처럼 모든 이벤트를 루틴 하나가 다 받게 만들면, 그 루틴이 모든 객체의 상호작용을 알아야 해서 결합도가 오히려 올라간다. (거대한 switch문 / if-else 지옥)

**출판/구독(Publish/Subscribe)**

- 구독자는 관심 있는 이벤트만 출판자에게 등록한다.
- 출판자는 구독자 목록을 들고 있다가 이벤트가 생기면 차례로 알려준다.
- 필요 없으면 구독 해제.
- 변형: 중앙에서 메시지를 배달하는 소프트웨어 버스, 채널에 밀어주는(push) 방식 / 클라이언트가 당겨가는(pull) 방식 등.

**MVC (모델-뷰-컨트롤러)** — 스프레드시트에 표, 막대그래프, 합계 상자가 있다고 해도 데이터는 한 곳(모델)에만 둔다. 뷰는 그 데이터를 보여주는 방식일 뿐이다.

- **모델**: 대상을 나타내는 추상 데이터. 뷰나 컨트롤러를 직접 모른다.
- **뷰**: 모델을 해석하는 방법. 모델의 변화를 구독한다.
- **컨트롤러**: 뷰를 제어하고 모델에 새 데이터를 넣는다.

같은 모델에 여러 뷰, 여러 모델에 하나의 뷰도 가능하다. Java의 트리 위젯은 `TreeModel` 인터페이스만 맞춰서 데이터를 주면 트리 UI가 그냥 생긴다. 아이콘 바꾸는 요구가 들어와도 렌더러만 바꾸면 된다.

**GUI가 아니어도 된다** — 야구 중계 시스템 예시. 점수, 타자, 날씨 등 모델이 있고, "점수 집계 뷰", "타자 통계 뷰", "기록 갱신 확인 뷰", "토막 지식 뷰"가 이를 구독한다. 이 뷰들이 다시 상위 객체의 모델이 되고, 그 위에 "아나운서용 프롬프터", "TV 자막", "웹페이지" 뷰가 붙는다. 모델-뷰가 **네트워크**를 이루면서 각 연결마다 결합이 끊긴다.

- 복잡할수록 모델 내부와 모든 이벤트를 보여주는 **디버깅 뷰**를 만들어 두면 시간을 많이 아낀다.
- 그래도 출판자와 구독자는 공통 인터페이스 정도는 서로 알아야 한다. 이것까지 끊는 게 다음 주제, 칠판이다.

(React의 상태 → UI 렌더링, 상태 관리 라이브러리의 subscribe, DOM `addEventListener` 모두 같은 아이디어다.)

### 칠판

> **TIP 43. 칠판을 사용해 작업흐름을 조율하라.**

형사들이 사건을 풀 때 칠판에 "험프티 덤프티: 사고인가 살인인가?" 하나 적어두고, 각자 증거, 증언, 추리를 붙인다.

- 형사들은 서로의 존재를 몰라도 된다. 칠판만 보고, 칠판에만 쓴다.
- 각자 배경도, 소속도 다를 수 있다.
- 수사 중에 사람이 들어오고 나가도 된다. 교대 시간이 달라도 된다.
- 칠판에 붙일 수 있는 것에 제한이 없다.

**칠판 시스템**은 지식의 생산자와 소비자가 **익명으로, 비동기적으로** 데이터를 주고받는 공간이다. 객체 간 결합을 완전히 끊을 수 있고, 작성할 코드도 줄어든다.

JavaSpaces 같은 시스템은 키/값(튜플 공간) 모델에 객체를 통째로 저장하고, 템플릿으로 찾아온다. 핵심 연산은 네 개뿐이다.

| 연산 | 기능 |
|---|---|
| read | 공간에서 데이터를 찾아 읽는다 |
| write | 공간에 넣는다 |
| take | 읽고 공간에서 제거한다 |
| notify | 템플릿에 맞는 객체가 쓰이면 알림을 받는다 |

인터페이스가 이것 하나라는 게 큰 장점이다. 분산 시스템에서 상호작용마다 API를 따로 만들다 보면 조합이 폭발한다.

**예: 대출 심사 시스템**

- 데이터 도착 순서가 보장되지 않는다. (신용 조회는 오래 걸리고, 이름/주소는 바로 확인)
- 여러 시간대, 여러 사무실에서 사람들이 데이터를 모은다. 일부는 외부 시스템이 자동으로 보낸다.
- 어떤 데이터는 다른 데이터에 의존한다.
- 새 데이터가 오면 새 질문이나 정책이 생긴다. (신용이 나쁘면 서류 5개 추가...)

모든 경우의 수를 워크플로로 짜면 복잡하고 규정 바뀔 때마다 다시 짜야 한다. 대신 **칠판 + 규칙 엔진**을 쓰면, 사실이 칠판에 올라올 때 해당 규칙이 실행되고, 그 결과가 다시 칠판에 올라가 다른 규칙을 깨운다. 도착 순서는 상관없어진다.

칠판이 너무 지저분해지면 구역을 나누거나 계층 구조로 정리하자.

(Redux store, 이벤트 버스, Kafka 토픽 같은 메시지 브로커가 현대판 칠판에 가깝다.)
